# Phase24 TDD·집중 검증과 후속 종합검증

> 2026-09-11 재계획: Phase24는 부분 구현 기준선으로 보존하고 미완료 범위를 [Phase25](../../phase25/README.md)로 이관했다. 아래 계획/실적은 당시 기록이며 전체 마일스톤 완료가 아니다. 현재 잔여 작업의 정본은 [32건 재점검 대장](../../phase25/GAP_AUDIT.md)이다.


2026-09-11 · **시험 설계만 작성. 이 문서의 시험 ID는 실행 결과가 아니다.**

사용자 결정: 개발은 TDD로 수행한다. 개발 중 검증은 작고 빠르게 유지하고 다음 별도 실행에서 종합검증을 수행한다. 실제 건물 시험은 요청 전까지 하지 않는다. 모든 업무 모듈은 구현 단계부터 WebMCP 제어를 시험한다.

## 1. 실행 수준

| 수준 | 언제 실행 | 범위·계획 예산 | 남기는 근거 |
| --- | --- | --- | --- |
| L0 기능 TDD | 동작을 바꿀 때 | 규칙/함수 1개와 경계 입력 몇 개. 목표 수 초 | RED/GREEN/정리 후 결과, 독립 기대값, 원인 |
| L1 영향 계약 | 한 작업 패키지의 의미 있는 변경을 마칠 때 | 변경 파일의 직접 호출/입력·저장·WebMCP 계약. 목표 약30초 이내 | 선택 이유·명령·소요시간·결과 |
| L2 작은 통합/시각 확인 | M8 도면, M9 전체 연결 시 | 부재/접합/기초가 적은 합성 예제 1개, 최소 조합, 도면1~2쪽. 자동 계산 목표60초 이내; 시각 확인 별도 | 해당 화면/산출물·상태·데이터 일치 |
| Q 종합검증 | 다음 사용자 요청 실행 | 고정 후보의 전체 회귀·독립 수치·환경·장기 메모리·출력 범위 | 새 커밋 기준 evidence와 자격 판정 |

위 시간은 **아직 측정하지 않은 개발 운영 목표**다. 실행 시간을 기록해 fixture 크기와 범위를 조정한다. 시간 초과는 합격이 아니며 필수 오류 시험을 삭제해 시간을 맞추지 않는다. 큰 행렬/실제 브라우저/장시간 반복이 원인이라면 기능 검증용 작은 사례와 환경 검증을 분리해 후자를 Q 대기표에 남긴다. 수정한 동작의 핵심 시험이 실패하면 해당 milestone은 미완료다.

L0/L1을 통과할 때마다 전체 suite를 반복하지 않는다. M9에서도 과거 21개 비교나 실제 건물을 실행하지 않는다. 소스가 바뀌지 않고 새 문제가 없으면 동일 검사를 거듭 돌리지 않는다.

## 2. TDD 작업 순서

1. 요구/결함 ID, 적용 규칙·범위, 수정 책임과 기대 결과를 한 작업 단위로 고정한다.
2. 최소 fixture를 만든다. 필요한 N/V/M·조합·상세만 넣고 큰 저장본·실제 현장 데이터에 의존하지 않는다.
3. 독립 기대값과 허용오차를 구현 전에 작성한다. 수치 규칙은 기준 조항·단위·산식의 독립 계산을, 제어 기능은 관찰 가능한 변경/상태를 기대값으로 삼는다.
4. RED를 실행하고 실패가 목표 결함 때문인지 확인한다. 새 API가 없어 실패한 것은 계약 RED로, 기존 수치가 잘못된 것은 수치 RED로 구분한다. import 오류만으로 수치 결함 재현을 주장하지 않는다.
5. 최소 수정으로 GREEN을 만든다. 기존 예상값을 현재 출력으로 덮어써서 통과시키지 않는다. 예비식 교체에 따른 의도된 값 변경은 근거·구/신 규칙·영향을 먼저 기록한다.
6. 중복 계산·숨은 기본값·책임 경계를 정리하고 같은 L0와 직접 영향 L1만 재실행한다. 수치 kernel 전체를 UI/WebMCP adapter 테스트마다 재실행하지 않는다.
7. 기능의 WebMCP definition→제품 서비스→결과까지 작은 계약 시험을 수행한다. schema 등록이나 도구 개수만 검사하고 완료 처리하지 않는다.
8. 실제 명령·시간·결과·커밋/working diff hash·미검증 범위를 상태/로그에 기록한다. 구현·집중검증·종합검증·출시 자격을 각각 기록한다.

단순 문서·색상 등 낮은 영향 변경에 형식적인 테스트를 추가하지 않는다. 계약/수치 오류를 예방하는 시험에 시간을 쓴다.

### 독립 기대값과 허용오차

- schema/상태/참조/건수/버전은 정확 일치로 검사한다. 숫자 오차를 이유로 상태·identity 불일치를 허용하지 않는다.
- 수치는 `absError <= absTol + relTol × abs(reference)`의 형식을 사용하고 **항목별** 단위/absTol/relTol과 근거를 fixture에 고정한다. 단일 임의 퍼센트를 모든 힘·길이·처짐에 적용하지 않는다.
- 단면·기초 산식의 수치 oracle은 운영 모듈을 import하지 않는 독립 계산/검토표다. 실제 규칙의 계수·감소율·적용 범위는 고정한 기준을 따른다. 테스트를 위해 chosen constant를 쓰면 합성 계약 시험으로 명시한다.
- 예: T09는 허용 총 Av=200mm², 최소 s=75mm, 요구 Av/s=4mm²/mm인 **합성 선택기 계약**으로 만든다. 최대 제공량 약2.667mm²/mm이므로 부족해야 한다. 이 수치를 실제 배근 추천이나 기준값으로 사용하지 않는다.
- 예: T15의 중심압축 접지압 oracle은 N=400kN, A=4m², 별도 자중=0인 **합성 산술 사례**에서 q=100kPa다. 지반 적합 판정은 별도로 입력한 조건과 규칙에 따라 평가한다.
- 설계 한계 바로 아래/위 두 사례를 함께 둔다. 허용오차는 비교 오차를 다루며 ratio가 한계를 초과한 후보를 합격시키는 여유값으로 쓰지 않는다.
- 부호 반전·축 회전·단위 등가·제약 불변·하중 비례성 같은 성질은 각 수치 모듈에서 필요한 작은 사례만 사용한다. 철근 증가 단조성도 적용 범위/상한 조건을 한정하고 모든 상세에서 항상 안전하다고 가정하지 않는다.

## 5. 파일과 실행 도구 제안

구현 시 `tests/p24-m0-scope.mjs`부터 `tests/p24-m9-workflow.mjs`처럼 기존 phase 시험 관례를 따른다. 실제 분리는 규칙 책임에 맞게 하고 큰 파일 하나에 모든 solver/UI/브라우저를 묶지 않는다. 공통 fixture는 `tests/fixtures/p24/`, 검증 명세는 `verification/specs/phase24/`에 둔다.

`tools/run-phase24-tests.mjs`는 **신설 제안**이다. 기본은 실행 대상을 요구하거나 목록만 반환하고 선택 없이 전체 suite를 돌리지 않는다. 제안 사용 형태:

```text
node tools/run-phase24-tests.mjs --list
node tools/run-phase24-tests.mjs --milestone=M4 --case=T09
node tools/run-phase24-tests.mjs --milestone=M4 --focused
```

이 문단은 최초 제안 기록이다. 이후 runner와 일부 집중 시험을 구현했다. 현재 존재/실행 결과는 tools/run-phase24-tests.mjs와 IMPLEMENTATION_STATUS.md를 따른다. 기본 실행에 Q·실제 건물·전체 phase runner를 숨겨 넣지 않는다.

직접 영향 검사로 재사용을 검토할 기존 파일은 `tests/p7-m1-material-registry.mjs`, `p21-m1-rc-contract.mjs`, `p21-m2-input-persistence.mjs`, `p21-m3-execution-selection.mjs`, `p21-m4-review-artifact.mjs`, `p22-focused.mjs`, `p23-rigid-gpu-focused.mjs` 등이다. 실제 변경 경로·실행 시간을 보고 필요한 사례만 선택한다. 기존 파일 전체를 매번 필수 실행으로 지정하지 않는다.

## 6. 개발 증거와 기록

제안 위치: `verification/evidence/phase24/m<번호>/<run-id>/`. 원본/실패 실행을 덮어쓰지 않는다. 개발 중 저장하는 것은 작은 fixture 참조와 요약이며 매 함수 시험마다 대형 PDF·전체 모델 dump를 생성하지 않는다.

manifest에는 다음을 남긴다.

- source commit, working diff hash/변경 파일, 날짜·실행환경·규칙/fixture 버전.
- 요구/결함/시험 ID, exact command, 시작/종료 시간·실제 elapsed, exit/result.
- RED 원인, 독립 기대값·오차, GREEN 결과, refactor 후 직접 영향 시험.
- WebMCP 실제 definition 경유 여부, mock/native/host 구분, 사용한 source/identity.
- 도면/보고서가 있으면 artifact hash·snapshot ID·시각 확인 대상 페이지.
- deferred 목록의 ID·미검증 이유·후속 실행 범위. 수행하지 않은 것은 `NOT_RUN`, 확인 자료가 없는 것은 `NO_EVIDENCE`.

`IMPLEMENTATION_STATUS.md`는 milestone의 구현 상태와 집중/종합검증 상태를 별도 칸에 둔다. `EXECUTION_LOG.md`는 실패·수정·판단을 append-only로 기록한다. 사용자 독립 검토는 기존 결정대로 사용자가 담당하며 개발자의 자체 시험 결과와 분리한다.

## 8. 완료 판정

마일스톤 완료에는 구현, 해당 L0/L1, 해당 모듈 WebMCP 제어, 필요한 작은 시각 확인, 기록이 필요하다. 각 항목을 생략했으면 사유와 남은 작업을 남기고 그 범위를 완료로 표시하지 않는다.

M9의 목표 표기는 `IMPLEMENTED / FOCUSED_VERIFIED / COMPREHENSIVE_PENDING`이다. 종합검증과 사용자 검토를 마친 뒤에만 지원 범위별 생산 자격을 판정한다. 종합검증을 나중에 한다는 사용자의 결정은 개발 중 거짓 OK·누락 검토·잘못된 재사용을 허용한다는 뜻이 아니다.
