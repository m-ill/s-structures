## 해결할 문제

1. **버전·표시 의존성:** `agentManifest.js`가 버전 상수를 얻기 위해 수치 모듈을 직접 import한다. 표시 정보와 계산 구현의 로딩 의존성을 분리한다.
2. **결과 준비:** 이미 존재하는 `prepareResultView`와 저장 결과 조회를 확장한다. 상세보고서·진단 builder 안의 파생 계산을 명시적 준비 단계로 옮긴다.
3. **탄성 실행 조정:** `linear3d.js`가 정적 결과 외에 동적 해석·강재 설계까지 조정한다. 순수 해석 단계와 제품 실행 순서를 분리한다.
4. **호환 경로:** 초기 trace·legacy·production MDOF와 여러 sparse 경로의 역할, 허용 소비자, 이행 조건을 명시한다.

## 진행 순서

**M0 기준선·소비자 목록 → M1 metadata·표시 분리 → M2 결과 준비 경계 → M3 탄성 실행 조정 → M4 호환 경로 정리 → M5 통합 검증·패키징**

M0에서 네 영역의 소비자를 함께 조사한다. 이후 M1과 M2의 독립 파일 작업은 병행할 수 있으나, 공통 API 계약과 파일 이동은 순차적으로 통합한다. M3는 M2의 결과 준비·입력 식별 계약을 사용하고 M4는 최종 소비자 그래프를 닫는다. 각 단계는 집중 검증 후 다음 단계로 넘어가며, 전체 후보 검증은 M5에서 한 번에 고정한다.

## 최종 결과

- 버전/표시 정보는 수치 구현을 불러오지 않고 제공한다.
- 제품 조회·보고서 렌더링은 준비된 동일 run snapshot을 읽는다. 입력 진단은 분석 결과와 별도 식별을 가진다.
- 정적 해석 core는 동적 solver·설계 함수를 호출하지 않는다. 필요한 순서는 제품 조정 계층에서 명시한다.
- 기존 공개 동기 API는 호환 façade로 보존하고, production 경로와 초기 trace 경로를 구분한다.
- 수정 전후 수치와 UI·Agent·WebMCP 결과를 비교할 수 있는 소스·manifest·로그·해시·호환 목록을 남긴다.

문서의 새 경로·API·시험명은 **제안**이다. M0에서 실제 소비자와 export 계약을 확인해 확정하며, 문서 존재를 기능 구현이나 검증 완료로 표시하지 않는다.
