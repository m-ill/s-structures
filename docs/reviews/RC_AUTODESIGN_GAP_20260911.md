# RC 예비 검토 NG·미검토 원인과 자동 설계 연결 결손

2026-09-11 · 저장된 Phase21 결과를 재집계하고 현재 소스와 대조함. 실제 건물 재해석·시험·입력 변경 없음.

## 근거

- 원본 결과: `output/phase21/m6-pilot-node-r5/review.json`
- 입력: `output/phase21/m6-pilot-node-r5/input-book.json`의 pages[0].model
- 이전 설명: `docs/archive/phase21/PILOT_RETEST_REPORT.md`
- 현재 소스 기준: ed24e04

NG 76건은 RC 부재 내력 실패만을 센 값이 아니다. concrete/connection/foundation/serviceability가 합쳐진 5,724개 검사 행의 집계다. 같은 부재가 여러 조합에서 반복 집계된다. 기존 'RC 검토 NG 76건·실패 부재 13개' 문구는 이 구분 없이 읽으면 오해를 만든다.

## 정확한 분해

| 상태 | 범주 / 항목 | 행 수 | 고유 대상 |
| --- | --- | --- | --- |
| NG | concrete / rc-shear-y | 32 | 보 5개 |
| NG | connection / preliminary-force-screen | 44 | 기둥 8개 |
| NOT_CHECKED | foundation / required-bearing-area | 120 | 기초 지점 6개 × 조합 20개 |

전단 NG 보: BX10(2건), BX11(13건), BX12(2건), BX20(2건), BX21(13건).

접합부 가정 비교 NG 기둥: C100(5건), C101(14건), C102(2건), C110(5건), C111(14건), C112(2건), C201(1건), C211(1건).

따라서 '실패 부재 13개'는 5개 보의 콘크리트 전단 비교와 8개 기둥의 임의 접합부 용량 비교를 합친 값이다. RC 기둥 8개가 축력·휨에서 실제 내력 부족으로 판정됐다는 뜻이 아니다.

## 1. 보 전단 NG 32건

지배 행은 BX11 / MAX-EX-P / Direct X다. 수요 143.094972977 kN, 내력 84.323684395 kN, 비 1.696972494.

`src/design/concrete.js`의 shearCheck는 `capacity=phi*vc`, `expression='Vu / phiVc'`, `provided=null`이다. 초과 수요에서 requiredRebar.AvsY/AvsZ는 계산하지만 제공 스터럽의 내력을 더하는 경로는 없다. 따라서 배근비를 늘리거나 별도 추천 스터럽을 생성해도 이 함수의 전단 판정은 변하지 않는다. 현재 가정에서 콘크리트 전단 기여만으로 부족하다는 판정이지, 실제 배근된 보의 최종 전단 실패를 입증한 결과가 아니다.

입력은 RC 300×500 보, Fc24, 피복 가정 0.05m, 철근 fy400이며 designParams.members는 비어 있다. 주근도 명시 배근표가 아니라 보 1%·기둥 1.5% 기본 철근비에 의존한다.

자동 설계의 첫 수정 대상은 제공 주근/스터럽의 명시적 데이터 계약과 내력 검토다. 그 다음 허용 철근 직경·다리 수·간격 후보를 생성하고, 전단 내력 상한·최소 배근·간격·정착 등 적용 기준 검토를 통과하는 후보를 선택해야 한다. 배근만으로 불가능할 때 단면 변경과 구조 재해석으로 넘어간다. 여기서는 실제 배근안을 선정하거나 합격으로 재판정하지 않았다.

## 2. 접합부 NG 44건

`src/design/connectionFoundation.js`는 재료·접합 상세를 구분하지 않고 모든 부재에 다음 지표를 적용한다.

`equivalent = hypot(Nmax,Vymax,Vzmax) + 0.05*hypot(Mymax,Mzmax)`

이를 nominalConnectionCapacity와 비교한다. 저장 입력에는 connectionParams가 없어 기본 250kN을 사용했다. 지배 C101은 419.082271950 / 250 = 1.676329088이다. 서로 다른 위치에서 나온 최대값을 합치는 예비 지표이며 RC 보-기둥 접합부의 동시 작용력·접합부 치수·전단·정착·구속철근 내력을 검토한 값이 아니다.

이 44건은 최종 RC 접합부 실패로 표현하면 안 된다. 구조 형식에 맞는 검토가 없으면 '접합 상세 검토 필요'로 구분하고 예비 수요 지표는 보존해야 한다. 기본 용량을 임의로 키워 NG를 지우는 것은 자동 설계가 아니다. 자동 보완은 실제 RC 접합부 검토 모듈과 상세 입력을 연결한 후 가능하다.

## 3. 미검토 120건

N000/N001/N002/N010/N011/N012 여섯 지점 모두 20회씩이다. 전체 120행의 checkId는 required-bearing-area이며 ratio/capacity는 null이다.

입력에는 foundationParams가 없다. 예비 모듈은 기본 허용지지력 150kPa로 `requiredArea=abs(Rz)/allowableBearing`만 산정한다. `src/compute/product/elasticReviewService.js`의 연결부는 실제 기초 면적과 비교하지 않고 **항상 NOT_CHECKED**로 넣는다. 기초 치수 입력만 추가한다고 이 연결부가 자동으로 OK로 바뀌는 구현도 없다.

기초 형식·치수·확인된 지반값 및 SLS/ULS별 검토 기준이 필요하다. 해당 계약을 만든 후 실제 면적·편심 접지압·들림·활동·휨·전단·펀칭 등을 검토하고 기초 후보를 탐색해야 한다. 지반값을 추측해 합격시키는 방식으로 자동화할 수는 없다.

## 4. 이미 있는 추천 코드와 끊어진 연결

- `src/design/rcDetailing.js`: 필요 주근 면적과 Av/s로 배근 후보를 추천하지만 원래 check.status를 이어받는다. 추천 배근을 모델에 확정하고 다시 내력을 계산하는 단계가 없다.
- `src/design/rc/beam.js`: 별도의 상세 trace를 만든다. 현재 elasticReviewService의 집계는 runDesignChecks의 예비 콘크리트 판정을 사용하며 이 상세 trace를 설계 폐회로로 사용하지 않는다.
- `src/modeling/designInputCommands.js`: member-design의 공개 변경 필드에는 피복·fy·철근비 등이 있으나 As/AsZ/AsY/AsTotal 및 스터럽 직경·다리·간격·기초 상세 필드는 포함되지 않는다. 내부 면적 계산 기능과 WebMCP 입력 계약도 불완전하게 연결돼 있다.

추가 코드 결함: selectStirrups는 요구 간격이 하한보다 작아도 하한으로 잘라 반환하고 부족 상태를 반환하지 않는다. detailRcBeam은 `stirrup.status || 'OK'`를 쓰므로, 제공 Av/s가 요구값보다 작아도 전단 상세 상태가 OK로 표시될 수 있다. 이는 이번 32건 NG의 원인은 아니지만 자동 선택에 사용하기 전에 수정해야 한다.

## 개발 우선순위

1. 집계·표시: RC 부재/접합부 예비 지표/기초 미검토와 고유 부재·조합별 행 수를 분리한다. 미검토를 입력 누락·미지원 계산·미연결 검토로 분류한다.
2. 설계 검토기: 제공 배근 기반 내력 및 각 검토의 적용성·실패 사유를 구현한다. 스터럽 선택 부족 시 OK가 되는 경로를 먼저 막는다.
3. 설계 입력: 실제 배근·기초 상세·근거 지반값을 버전 관리하며 UI/WebMCP로 읽고 변경한다.
4. 자동 보완: 원본 보존 → 변경 후보 → 필요한 재해석 → 모든 해당 검토 재실행 → 전후 비교 → 비용/단면/시공성 제약으로 후보 선택. 단면·강성이 바뀌면 기존 해석 결과를 재사용하지 않는다.
5. 종료 조건: 단순 NG=0이 아니라 필수 검토 coverage, 미검토 사유, 적용 기준, 모델/해석/배근 identity 일치까지 확인한다.

현재 미검토 120건은 존재하는 검사 행의 수다. 접합부·정착·구속·펀칭 등 문구로만 제한된 미구현 검토는 그 120건에 모두 포함되지 않는다. 이를 없애더라도 최종 설계 완성을 뜻하지 않는다.
